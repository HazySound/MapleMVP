# 블랙 등급 PC방 보정 (2026-09-27 제보)

블랙 등급에서 PC방 보정이 전혀 진행되지 않는다는 제보를 받고 고친 내용이다.
원인이 둘이고 둘 다 블랙에서만 생긴다. 옮겨 다니며 이어서 볼 수 있게 여기 적어 둔다.

## 증상

`👀 12줄 표가 보여요 / 표는 보이는데 숫자가 맞지 않아요`에서 114장을 읽어도
넘어가지 않는다. 제보자 환경은 모니터 3440x1440, 인게임 1920x1080.

해상도는 원인이 아니었다. 제보 캡처를 인식기에 넣으면 표는 완벽하게 읽힌다.

```
104,568 / 771,531 / 772,224 / 822,024 / 822,024 / 1,325,364
1,325,364 / 1,396,164 / 1,396,164 / 1,396,164 / 2,201,034 / 2,476,134
```

막힌 곳은 판독이 아니라 검증(`acceptReading`)이었다.

## 원인 1 — 블랙은 위 등급이 없다

다른 등급은 상단에 `레드 등급까지 590,330 캐시` 같은 줄이 있고, 이 한 줄에서
지금 13주 합계를 역산한다(`anchor`). 블랙은 위가 없어 이 줄 자체가 인게임에 없다.
코드는 이 줄이 반드시 있다고 가정하고 있었다.

## 원인 2 — 이월이 '유지까지'에서 미리 빠져 있다 (진짜 막은 쪽)

블랙은 갱신 때 모자란 금액을 이월에서 자동으로 꺼내 쓴다. 그래서 인게임이 적어 주는
`현재 등급 유지까지`는 그 줄에서 쓰일 이월을 **이미 빼고** 적은 금액이다.

```
k주 뒤 13주 합계 = 2,500,000 − 유지까지_k − 사용이월_k
```

이월을 되돌리지 않으면 이웃한 두 줄의 차이가 이월만큼 부풀어, 그 주 금액이 틀린다.
제보 캡처에서는 1주 뒤 줄 하나만 16,132원 어긋났고, 그 결과
`(주차 금액 − 수집한 결제) % 100 == 0` 검증에 걸려 모든 후보가 탈락했다.

```
1주 뒤 → 2주 뒤 차이 = 666,963   (이월이 섞인 값)
실제로 빠지는 주       = 650,831   (666,963 − 16,132)
```

## 고친 방법

이월 금액을 화면 숫자 더미에서 골라내려 했으나 실패했다. 오독한 값(`1,632`)이
진짜 값(`16,132`)과 끝 두 자리가 같아서 둘 다 검증을 통과했고, 가릴 수 없었다.

대신 **툴팁 맨 오른쪽 `사용 이월 금액` 열을 자리로 찾아 읽는다.** 금액 열 오른쪽에
같은 줄로 붙어 있는 열을 읽으면 `[16132, 0, 0, …, 0]`이 깔끔하게 나온다.
임계값·블러 조합을 다 돌려도 답이 하나뿐이라 흔들리지 않는다.

이월 0을 **먼저** 시도하고 실패할 때만 이 열을 쓴다. 그래서 블랙이 아닌 사람에게는
아무것도 달라지지 않고, 이월 해석이 틀렸더라도 기존 동작이 그대로 남는다.

`W1~W12 합계 = 2,379,300`, 1주 뒤 시점의 13주 합계와 원 단위까지 일치한다.

```
그 주 PC방 = 그 주 넥슨 기준 금액 − 그 주 수집한 결제
```

## W0는 왜 못 구하나

툴팁 12줄은 모두 `k주 뒤 시점의 13주 합계`를 준다. W0는 1주 뒤 갱신에서 이미
빠져나간 주라 **어느 줄에도 들어 있지 않다.** W0가 등장하는 식은 하나뿐이다.

```
지금 13주 합계 = sum_1 + W0
```

좌변을 주는 것이 `○○ 등급까지` 한 줄인데 블랙에는 그게 없다. 구매내역을 더해도
안 된다. 구매내역은 `수집한 결제`를 줄 뿐이고, W0에서 모르는 것은 PC방 쪽이다.

같은 툴팁을 보이면서 W0만 다른 사람이 실제로 존재할 수 있다는 뜻이기도 하다.

### `유지까지` 금액이 곧 W0 아닌가? — 아니다, 하한선이다

`유지까지`는 **앞으로 더 결제해야 할 금액**이지 빠져나가는 주의 금액이 아니다.

```
need_1 = 2,500,000 − sum_1 − 이월      (기준선에서 잰다)
W0     = 지금 13주 합계 − sum_1         (지금 합계에서 잰다)
```

둘이 같으려면 `지금 13주 합계 + 이월 = 2,500,000`, 즉 **지금 딱 블랙 커트라인에
걸려 있어야** 한다. `restore`로 말하면 `total = tierTh − carry`를 가정하는 것과 같다.

다만 지금 등급이 블랙이라는 사실에서 `지금 13주 합계 + 이월 ≥ 2,500,000`이 나오므로,

```
W0 ≥ need_1 = 104,568
```

**하한선으로는 맞다.** 화면에 넣지는 않았다. 확정값처럼 읽힐 여지가 있고 어차피
다음 목요일이면 창 밖으로 나가는 값이다.

### 구멍은 저절로 메워진다

| | 13주 창 | 상태 |
|---|---|---|
| 1회차 스캔 | W0~W12 | W1~W12 확정, **W0만 구멍** |
| 2회차 스캔 (다음 주) | W1~W13 | W1~W12는 1회차에 저장됨, W13은 이번에 계산 → **구멍 없음** |

블랙 유저도 첫 스캔 한 번만 1주가 비고, 그 뒤로는 13주가 다 채워진다.
스캔 간격이 12주를 넘지만 않으면 된다.

  되어 있으나 실물 캡처로 확인하지 못했다.

### 남은 검증 방법

두 해석은 1주 뒤 줄에서 16,132원 차이가 나고, 이는 100의 배수가 아니다. 따라서
`(주차 금액 − 수집한 결제) % 100 == 0` 규칙에 **둘 중 하나만 통과한다.**

- 2~12주 뒤 11주는 두 해석이 같은 값을 낸다 → 이것으로 제보자를 특정할 수 있다
- 그다음 1주 뒤 한 줄로 어느 해석이 맞는지 판정된다

D1에 쌓인 구매내역으로 배포 전에 미리 가릴 수 있다. 다만 남의 결제 기록이라
운영자가 직접 돌려야 한다(에이전트 쪽은 PII 가드에 걸린다). 판정표:

| 결과 | 뜻 |
|---|---|
| 이월 해석만 통과 | 지금 고친 대로 맞다 |
| 이월 없는 해석만 통과 | 수정을 되돌려야 한다 |
| 둘 다 통과 | 우연히 겹쳤다, 못 가린다 |
| 둘 다 탈락 | 이월이 아니라 구매내역 수집 누락이 원인 |

조회를 안 하더라도 **제보자가 재시도하면 같은 판정이 난다.** 코드가 이월 0을 먼저
시도하기 때문이다. 실패하면 오류 문구에 어느 주에서 몇 원이 어긋나는지 찍힌다.

남는 위험은 하나. 구매내역에 수집 누락이 있고 그 금액이 하필 이월과 끝 두 자리가
같으면(1% 확률) 엉뚱하게 통과할 수 있다. 이것은 D1을 봐도 구분되지 않는다.
